# 2026-08-13 — 더미 데이터 설계부터 Org 적재까지

**한 줄 요약** · 구글시트 메타데이터 정의서를 기준으로 데모용 더미 데이터를 만들고 Data Loader로 Org에 넣었다. Object 15종 약 270건. 넣는 과정에서 문서와 실제 Org가 다른 지점을 10개 넘게 찾아냈다.

---

## 오늘의 목표

데모 리허설을 하려면 시나리오가 **실제 데이터 위에서** 돌아가야 한다. 지금까지 `docs/data/`에 값을 글로만 적어뒀는데, 이걸 실제 Org 레코드로 만드는 게 오늘 할 일이었다.

---

## 1. 데이터 규모 정하기

처음엔 팬 200명 규모로 잡았다가 두 번 갈아엎었다.

**첫 시도** — 실제 구단처럼 만들어보자는 생각으로 팬 200명, 선수단 65명, 경기 288건을 생성했다. 총 5,700건. 만들고 나서 계산해보니 Developer Edition의 데이터 저장 한도(5MB ≈ 2,500레코드)를 훌쩍 넘겼다. 애초에 들어가지도 않을 데이터를 만든 셈이다.

**두 번째** — 팀에서 정리한 권장 수량표를 받아 규모를 다시 잡았다. Fan 20명, Game 10경기, Order 30~50건. 총 **307건**으로 줄였다.

여기서 판단이 하나 갈렸다. 앞서 "선수단은 실제 야구단 규모로"라고 정했는데 권장 수량표는 Player를 5~8명으로 잡고 있었다. **데모에서 실제로 화면에 등장하는 선수는 문태양 한 명**이고 나머지는 최애 선수 선택지 역할뿐이라, 기본은 8명으로 가되 65명짜리 전체 선수단 파일을 따로 만들어뒀다. 나중에 선수 목록 화면을 만들게 되면 그때 교체하면 된다.

**규모를 줄이면서 지킨 원칙**은 하나다. **픽리스트 값이 전부 한 번씩은 등장하도록 배치했다.** 건수는 적어도 Position 4종, Product RecordType 4종, NBA 추천 6종, Benefit Type 4종, Notification Channel 4종, Case Status 4종이 다 들어간다. 한 번 적재하면 승우가 만든 필드 설정이 맞는지 전부 검증된다.

## 2. 팬 20명에게 각자 역할을 줬다

숫자만 채우면 Dashboard는 채워지지만 검증은 안 된다. 그래서 팬마다 **깨질 수 있는 지점**을 하나씩 맡겼다.

| 팬 | 검증하는 것 |
|---|---|
| 정하윤 · 안유진 (VIP) | **시즌권 1건으로 여러 경기 입장** — 티켓 1장 = 입장 1회 제약이 있으면 여기서 걸린다 |
| 김도현 → 최민재 | 산 티켓을 **양도**(구매자 ≠ 소유자) 후 경기 취소로 **환불** |
| 권도영 | 재방문 2회 · 지출 20,000원 — **VIP 후보 기준 바로 아래 경계값** |
| 송재현 | 만료된 작년 멤버십 (`Membership_Status__c` = Expired) |
| 박서연 | 2025·2026 두 시즌 Activity Pattern — **Fan+Season 중복 방지 규칙** 테스트 |

VIP 후보 감지 조건은 **재방문 3회 이상 + 누적 지출 10만원 이상**이다. 권도영을 일부러 그 바로 아래에 놓아서, Flow가 경계값에서 오작동하지 않는지 볼 수 있게 했다.

또 하나. 데이터에 **2026시즌 관중 급증**이라는 실제 흐름을 반영했다. 올해 KBO가 505경기 만에 900만 관중을 넘겼고 경기당 평균 관중이 전년 대비 6% 늘었다. 이걸 홈경기당 입장 기록 2.5건 → 4.5건, 신규 가입 팬 6명 → 12명, 유입 채널 중 SNS 비중 최다로 옮겼다. 데모에서 "요즘 팬이 늘고 있다"는 맥락이 데이터로 보이게 하려는 의도였다.

## 3. 적재하면서 막힌 것들

여기가 오늘의 대부분이었다. **한 번에 들어간 파일이 거의 없었다.**

### Data Import Wizard로는 애초에 안 됐다

Setup 안에 있어서 편할 줄 알았는데, 지원 Object가 Account·Contact·Lead·Person Account·커스텀 오브젝트로 한정이었다. **우리가 넣어야 할 Order, OrderItem, Product2, PricebookEntry, Campaign, Case가 전부 목록에 없었다.** Data Loader 하나로 통일하기로 했다.

### External Id 전략을 세웠다가 절반쯤 접었다

CSV끼리 서로를 가리키려면 임시 번호(`FAN-01`, `PRD-03`)가 필요한데, Salesforce는 이걸 모른다. 그래서 각 Object에 `External_Id__c` 필드를 만들고 Upsert로 넣는 방식을 택했다.

두 번 막혔다.

- **Insert에서는 안 된다.** External Id로 다른 레코드를 가리키는 기능은 **Upsert 전용**이다. Insert 마법사에는 그 화면(Step 2b) 자체가 없다. Insert로 넣으면 오류도 없이 관계만 조용히 비는데, 이게 제일 위험하다.
- **`Season__c`에는 External Id 필드가 없었다.** 요청한 필드가 일부 Object에만 만들어져 있었고, 그걸 05번 Game을 넣다가 `Id is not an External ID or indexed field for Season__c` 오류로 알았다.

결국 **실제 Salesforce Id를 CSV에 직접 채워 넣는 방식**으로 바꿨다. 부모를 넣고 → Developer Console이나 Export로 Id를 뽑고 → 자식 CSV에 채우는 걸 반복했다. 손은 더 가지만 확실하다.

### Record Type은 이름으로 못 넣는다

CSV에 `Player`라고 적어두면 안 되고 18자리 Id가 필요하다. Object Manager에서 Record Type을 열어 URL 끝의 Id를 복사해 넣었다.

그런데 넣었더니 이번엔 이 오류가 났다.

```
Record Type ID: this ID value isn't valid for the user: 012bm00001BQkQhAAL
```

Id는 맞는데 **쓸 권한이 없다**는 뜻이었다. Record Type을 새로 만들면 프로파일에 자동으로 할당되지 않는다. 관리자 계정이어도 Setup → Profiles → Object Settings에서 직접 체크해야 한다. Product2(4종)와 Person Account도 같은 문제를 겪을 게 뻔해서 한 번에 다 켰다.

### PricebookEntry가 제일 까다로웠다

- **커스텀 필드를 추가할 수 없는 Object**라 External Id를 못 만든다
- **OrderItem에는 상품(Product2)을 직접 넣을 수 없다.** PricebookEntry를 넣으면 상품이 따라온다
- **가격표 항목이 없으면 OrderItem이 아예 안 들어간다**

그래서 03번 상품을 넣고 → Export로 Product2 Id를 뽑고 → 04번 가격표를 넣고 → 다시 Export로 PricebookEntry Id를 뽑아 → 08번 OrderItem에 채우는 순서가 됐다.

중간에 `CostBook ID: id value of incorrect type: Standard Price Book`이라는 오류를 만났는데, `Pricebook2Id` 칸에 Id가 아니라 "Standard Price Book"이라는 **글자**를 넣어둬서 난 것이었다.

### Order는 Draft로 넣고 나중에 Activated

Salesforce는 **Draft 상태에서만 Order에 상품을 추가**할 수 있다. 그래서 Order를 Draft로 넣고 → OrderItem을 넣고 → Order를 Activated로 일괄 Update하는 3단계가 필요했다.

부작용도 있었다. **상품이 하나도 없는 Order는 Activated로 바꿀 수 없다.** OrderItem 3건이 실패했더니 그 Order 3건도 활성화가 안 됐다.

### 문서와 Org가 다른 지점들

정의서(구글시트)를 그대로 믿고 만들었더니 실제 Org와 어긋나는 게 계속 나왔다.

| 항목 | 문서 | 실제 Org |
|---|---|---|
| Benefit Object | `Benefit__c` | **`Benefits__c`** |
| Recommendation Object | `Recommendation__c` | **`Recommendations__c`** |
| `Position__c` | 투수/포수/내야수/외야수 | **1루수·2루수·좌익수·우익수** 등 세분화 |
| `Refund_Reason__c` | `[Ticket] 경기취소` | **`경기취소`** (게다가 Order Type 종속 픽리스트) |
| `Section__c` | 내야 지정석 | 값 세트에 없음 → **제한 픽리스트라 거부** |

`Section__c`는 실패한 3건이 전부 `내야 지정석`을 쓰는 행이라는 걸 보고 찾았다. Object Manager에서 열어보니 "값 세트에 정의된 값으로 제한"이 걸려 있었다.

**교훈은 명확하다. 설계 문서는 의도이고, 진짜 기준은 Org다.** 다음부터는 데이터를 만들기 전에 Object Manager에서 픽리스트 값을 먼저 확인해야 한다.

### Campaign은 권한이 하나 더 필요했다

Data Loader Object 목록에서 `Campaign`만 안 보였다. Campaign Member, Campaign Share는 있는데 정작 Campaign이 없었다. **Campaign 생성에는 User 레코드의 `Marketing User` 체크가 별도로 필요하다.** Data Loader는 "내가 만들 수 있는 Object"만 보여주기 때문에 목록에서 통째로 빠진 것이었다.

### 마지막에 통화 문제로 Order를 다 지웠다

가장 아팠던 부분이다. **Org 기본 통화가 USD였다.** 티켓 10,000원이 $10,000으로 들어가 있었다. 금액이 들어가는 Order 계열을 전부 지우고, Company Information에서 Currency Locale을 KRW로 바꾼 뒤 다시 넣기로 했다.

데이터를 만들기 전에 확인했어야 할 항목이었다. 스키마만 보고 Org 설정은 안 봤다.

## 팀에 공유할 것

적재하면서 발견한 것 중 나 혼자 정할 수 없는 것들.

1. **`Order_Type__c`에 `Season Pass` 값이 없다** — 시즌권 구매를 Ticket Purchase로 담아뒀는데, 픽리스트 값을 추가할지 정해야 한다
2. **`Membership_End_Date__c`와 `Coverage_End_Date__c`가 둘 다 남아 있다** — 결정대로면 Coverage로 통합됐어야 한다
3. **Contact(Player)에 1군/2군·보직 구분 필드가 없다** — Dashboard에서 "1군 선수만" 같은 필터가 필요하면 필드를 추가해야 한다
4. **시즌권 1건으로 여러 번 입장**이 가능한 구조인지 확인 필요
5. **Org에 다른 팀원이 넣은 데이터가 섞여 있다** — 상품 151건, 주문 14건. 우리 것은 `PRD-` 같은 접두사로 구분했지만 Dashboard 만들 때 감안해야 한다
