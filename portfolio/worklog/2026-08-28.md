# 2026-08-28 — 스폰서십 계약 이력 5년치와, Lead 전환 시 DART 공시 자동보강

**한 줄 요약** · 파이프라인이 "지금 이 순간"만 보여주던 걸 넘어, 2020~2024 스폰서십 계약 이력을 심어 "매년 갱신되는 장기 파트너십"이 데이터로 보이게 했다. Closed Won마다 라인아이템·Order·Asset을 붙여 상품·정산·현재 보유 권리까지 이어지게 만들었다. 이어서 **Lead 전환 시 기업 규모정보(매출·영업이익·자산총계)를 DART 공시에서 자동으로 끌어오는 보강 시스템**을 Apex로 구축·배포하고 프로덕션에서 E2E로 검증했다.

---

## 오늘의 목표

8/25까지 PRM은 Opportunity 100건으로 "파이프라인처럼" 보이게 만들어 뒀다. 그런데 스폰서십은 본질적으로 **매년 갱신되는 장기 관계**다 — 화면에 올해 딜만 있으면 "이 회사가 몇 년째 우리 스폰서인가", "갱신율이 얼마인가" 같은 질문에 답할 수 없다. 그래서 오늘은 ① 과거 계약 이력을 심어 시계열을 만들고 ② 계약이 상품·정산·현재 보유 권리로 이어지게 하는 게 첫 목표였다.

두 번째 목표는 성격이 다르다. 스폰서십 체결을 판단하려면 "이 회사가 얼마짜리 회사인가"(매출·영업이익·자산총계)를 알아야 하는데, 담당자가 매번 손으로 찾아 넣는다. 이걸 **Lead 전환 순간 공시 데이터로 자동 보강**하는 파이프라인을 만드는 것이 목표였다.

## 한 것

### 1. Opportunity 이름에서 단계(Stage)를 걷어냈다

기존 더미의 이름이 단계를 흘리고 있었다 — Closed Won은 `…공식 파트너십 계약`, 진행 중은 `…파트너십 제안`처럼. **StageName 필드가 이미 그 정보를 들고 있는데 이름에도 박아두면 이중관리**가 되고, 이력을 쌓을 때 단계가 바뀔 때마다 이름을 고쳐야 한다.

→ 모든 스테이지를 **`{회사} - {연도} 시즌 파트너십`** 한 가지 규칙으로 통일했다. 이름은 "누구와 언제"만 말하고, "어느 단계인가"는 StageName이 말한다.

### 2. 2020~2024 계약 이력 — "장기 파트너십" 시나리오

단순히 과거 레코드를 흩뿌리는 게 아니라 **갱신 서사가 성립하도록** 설계했다.

- **앵커 스폰서 18곳**은 매 시즌 갱신 → Type을 첫 해 `New Business`, 이후 갱신은 `Add-On Business`로 구분. "3년째 갱신 중인 파트너"가 데이터로 드러난다.
- **2차 스폰서 약 16곳**은 중간 시즌부터 합류 → 매년 신규 유입이 있는 것처럼 보인다.
- 각 Closed Won Opportunity에 **OpportunityLineItem**을 붙였다. 스폰서십 상품(아래 5번)에서 골라 담되, **라인아이템 합계가 각 Opp의 Amount와 정확히 일치하도록** 가격을 맞췄다. 8/25까지 금액만 있고 라인아이템은 비어 있던 2025/2026 딜도 이때 같이 채웠다.

**결과** — Opportunity 약 **253건**, OpportunityLineItem 약 **299건**.

### 3. Order · OrderItem 미러링 — 계정 화면에서 상품이 보이게

Opportunity의 라인아이템은 영업 화면에는 뜨지만 **Account 화면에서는 "이 파트너가 뭘 샀는지"가 안 보인다.** 그래서 Closed Won마다 같은 Account에 **Order(Activated · KRW · Standard Price Book)**를 만들어 라인아이템을 **OrderItem**으로 미러링했다. TotalAmount는 해당 Opp의 Amount와 일치시켰다.

- **Order 약 220건 · OrderItem 약 298건.**
- 🔴 **함정** — 이 Org의 `Order`에는 **`OpportunityId` 필드가 없다.** 그래서 Order는 Account에만 걸리고 Opportunity와 직접 연결이 안 된다. 추적을 위해 각 Order의 **`Description`에 `SPN-AUTO|<oppId>` 마커**를 심었다. 단 Description은 long-text라 **SOQL 필터가 안 된다** — 나중에 걸러낼 때는 이 점을 감안해야 한다(정확 매칭 불가, 조회 후 후처리 필요).

### 4. Asset — "지금 보유 중인 권리"

계약 이력(과거)과 별개로, **각 Account의 가장 최근 Closed Won 라인아이템**에서 **Asset(Status=Installed)**을 만들었다. 이게 "이 파트너가 현재 보유한 스폰서십 권리"를 나타낸다. 이력은 Order/Opp로, 현재 상태는 Asset으로 갈라두면 "지금 활성 권리만" 보는 화면이 깔끔해진다.

- **Asset 약 99건.**

### 5. 스폰서십 상품 체계 (배경)

위 라인아이템의 소스가 된 상품은 `Sponsorship` 계열 **Product2 21종**이다 — 패키지형(Diamond/Platinum/Gold, `SPN-PKG-*`)과 개별 권리형(`SPN-NAMING-ZONE`, `SPN-LED-BACKNET`, `SPN-UNIFORM-MAIN/SLEEVE`, `SPN-FENCE-OUTFIELD` 등). 전부 KRW로 Standard Price Book에 등재.

### 6. Lead 전환 시 DART 공시 자동보강 시스템 구축·배포

스폰서십 체결 판단용 규모정보(매출·영업이익·자산총계)를 **DART Open API**에서 자동 수집하는 파이프라인을 만들었다. 프로덕션 Org에 배포하고 E2E로 검증했다.

**라이프사이클**
```
1. Lead 전환 → Flow(DART_Lead_Convert_Match, Lead·IsConverted) → DartMatchInvocable
2. AI 매칭: DartMatchService가 Einstein Models API(aiplatform.ModelsAPI,
   모델 sfdc_ai__DefaultGPT4Omni)로 회사명→종목코드 추론.
   매핑 후보 그라운딩 + 환각 방지(매핑 실재 검증) → 제안 필드 기록, 상태=검토대기
3. 담당자가 리스트뷰(DART 매칭 검토대기)에서 확인 → DART_Match_Status__c=승인
4. Flow(DART_Account_Approved_Enrich, Account·상태→승인) → DartEnrichmentInvocable
   → DartEnrichmentQueueable가 제안 종목코드→corp_code→
     DART company.json + fnlttSinglAcnt.json 콜아웃 → 빈 필드만 채움, 상태=보강완료
```

**핵심 구성요소**
- **Apex**: `DartService`(콜아웃), `DartMatchService`(AI 매칭), `DartEnrichment`/`DartMatch` 각 Queueable+Invocable, 테스트 2종
- **Account 커스텀 필드**(영문 API명 + 한글 라벨): `Stock_Code__c`, `Business_Reg_No__c`, `Corp_Name_Eng__c`, `Market_Type__c`, `Operating_Profit__c`, `Total_Assets__c`, `DART_Match_Status__c`(비제한 픽리스트: 미매칭/검토대기/승인/거절/보강완료/매칭없음), `Proposed_Stock_Code__c`, `Proposed_Corp_Name__c`, `Match_Confidence__c`, `Match_Rationale__c`, `DART_Enriched_At__c`. (표준 병행: AnnualRevenue/Phone/Website/BillingStreet)
- **Custom Object** `DART_Corp_Mapping__c`: 상장사 **3,988건**(corp_code ↔ stock_code ↔ corp_name), `corpCode.xml`에서 적재
- **Custom Setting** `DART_Setting__c`(계층형·Public): `Api_Key__c`에 OpenDART 인증키
- **RemoteSiteSetting** `opendart_fss`
- **PermissionSet** `DART_Enrichment_Admin`: 신규 필드 FLS

**설계에서 판단이 갈린 지점** — 왜 AI가 6자리 종목코드를 반환하는데 별도 매핑 테이블을 뒀나. DART `company.json`은 **8자리 corp_code**를 요구하는데 LLM은 **6자리 stock_code**를 안정적으로 반환한다. 이 간극을 `DART_Corp_Mapping__c` 3,988건으로 변환한다. 동시에 이 매핑 테이블이 **환각 방지의 그라운딩** 역할도 한다 — LLM이 낸 종목코드가 실재하는지 여기서 검증하고, 매핑 후보를 프롬프트에 넣어 카카오/네이버/삼성전자/현대차 같은 주요 기업의 매칭 정확도를 크게 끌어올렸다.

## 막힌 것

> 이 섹션이 포트폴리오에서 제일 값어치 있다. 문제 → 원인 → 해결 순서로.

### Order를 Opportunity에 걸 수가 없다

계약 이력을 Order로 미러링하려는데 Order를 해당 Opportunity에 연결할 방법이 없었다.

**원인** · 이 Org의 `Order` 오브젝트에는 **`OpportunityId` 표준 필드 자체가 없다.** (표준 Order에는 있지만 이 Org 구성에서는 노출/활성화돼 있지 않았다.)

**해결** · Order는 Account에만 걸고, Opportunity와의 연결은 **`Description`에 `SPN-AUTO|<oppId>` 문자열 마커**로 대신했다. 단 Description은 long-text라 SOQL `WHERE`로 못 거른다 — 조회 후 코드에서 파싱하는 방식으로 감수했다.

**배운 것** · 표준 오브젝트라도 **Org마다 있는 필드가 다르다.** "표준이니까 당연히 있겠지"로 스키마를 가정하지 말고, 미러링처럼 관계에 의존하는 작업 전에는 실제 필드 존재를 먼저 조회해야 한다.

### 필드 API 이름에 한글을 못 쓴다

DART 보강 필드를 한글 이름으로 만들려다 배포가 거부됐다.

**원인** · 필드 **API 이름은 영문·숫자·언더스코어만** 허용된다. 라벨은 한글이 되지만 API명은 안 된다.

**해결** · **영문 API명 + 한글 라벨** 조합으로 통일(예: `Operating_Profit__c` / "영업이익").

### 배포가 1건 실패에 전체 롤백됐다

여러 필드를 한 번에 배포하다 하나가 막히자 나머지도 전부 안 들어갔다.

**원인** · 메타데이터 배포는 **all-or-nothing** — 한 컴포넌트가 실패하면 그 배포 전체가 롤백된다.

**해결** · 실패 원인(위 한글 API명 등)을 먼저 잡고 재배포. **부분 성공을 기대하지 말 것.**

### 프로덕션에서 Protected 커스텀 세팅이 안 된다

DART 인증키를 담을 `DART_Setting__c`를 Protected로 만들려다 막혔다.

**원인** · 프로덕션 Org에서는 **Protected 커스텀 세팅을 생성할 수 없다**(주로 패키지 컨텍스트에서만).

**해결** · **Public 커스텀 세팅**으로 만들었다. (키 관리 관점의 트레이드오프는 팀 공유 항목에 남김.)

### 새 필드가 Bulk/REST에서 "No such column"으로 보이지 않는다

방금 만든 필드에 데이터를 넣으려는데 컬럼이 없다고 나왔다.

**원인** · **FLS가 없으면** 필드는 존재해도 Bulk/REST API 레벨에서 "No such column"으로 취급된다. 또 Bulk API는 **잡의 LineEnding(LF) 설정과 CSV 파일의 실제 줄바꿈이 일치**해야 한다(순수 LF).

**해결** · PermissionSet `DART_Enrichment_Admin`으로 FLS를 먼저 부여하고, CSV를 순수 LF로 맞췄다.

### 픽리스트 값을 나중에 추가했더니 DML 검증이 계속 튕겼다

`DART_Match_Status__c`에 값을 추가한 뒤 그 값으로 업데이트하니 검증 오류가 났다.

**원인** · 제한 픽리스트에 값을 추가하면 **DML 검증 캐시 전파에 지연**이 있어, 방금 추가한 값이 한동안 거부된다.

**해결** · 이 필드는 **비제한(unrestricted) 픽리스트**로 두어 회피했다.

### Flow에서 invocable에 컬렉션을 넘길 수 없었다

Flow에서 `DartMatchInvocable`(입력 `List<Id>`)에 레코드 컬렉션을 넘기려다 안 됐다.

**원인** · Flow에서 invocable의 `List<Id>` 입력에는 **컬렉션 변수를 직접 넣는 게 아니라 스칼라(단일값)를 전달**해야 한다 — 플랫폼이 자동으로 벌크화한다.

**해결** · 단일 Id를 전달하도록 바꿔 자동 벌크 처리에 맡겼다.

## 팀에 공유할 것

혼자 정할 수 없는 것, 다른 사람 작업에 영향 가는 것.

1. **@전체 — 스폰서십 이력·Order·Asset 약 570건이 새로 들어갔다.** 전부 데모/설계 검토용이며 실제 계약이 아니다. Order는 `Description`의 `SPN-AUTO|<oppId>` 마커로 식별하되, **long-text라 SOQL 필터가 안 되니** 대량 조회 시 감안할 것.
2. **@Opportunity/Product 담당 — Order에 `OpportunityId`가 없다.** 이 Org 구성상 Order는 Account에만 걸린다. Order를 Opp에 직접 연결해야 하는 요구가 생기면 커스텀 Lookup을 추가할지 팀 결정이 필요하다.
3. **@전체 — DART 자동보강은 Lead 전환 파이프라인에 붙는다.** 혜준(Lead)→아론(Account) 경계에 자동화가 하나 더 생겼다. Lead 전환 시 `DART_Match_Status__c`가 "검토대기"로 세팅되고, 담당자 승인 후에야 규모정보가 채워진다 — **승인 단계(리스트뷰 "DART 매칭 검토대기")가 운영 흐름에 포함**된다는 걸 공유한다.
4. **@전체(보안) — DART 인증키가 Public 커스텀 세팅에 있다.** 프로덕션에서 Protected가 불가해 Public으로 갔다. 키 보호가 필요하면 Named Credential 등으로 옮기는 걸 후속 과제로 제안한다.
5. **@대량 적재 담당 — 8/19·8/25에 이어 다시 확인된 규칙**: 새 필드는 FLS 없으면 Bulk/REST에서 "No such column"으로 안 보인다. 적재 전 PermissionSet FLS 부여를 표준 절차로.
