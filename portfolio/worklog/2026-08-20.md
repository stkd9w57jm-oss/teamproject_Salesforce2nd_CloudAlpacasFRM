# 2026-08-20 — Lead Convert 실검증, PRM 더미 데이터, Partner 화면 계층 구축

**한 줄 요약** · 제휴사 레코드가 팬 화면으로 뜨던 문제를 Partner 전용 Layout·Compact Layout·Lightning Record Page로 분리했다. Lead Convert를 실제로 돌려 Account·Contact·Opportunity가 한 번에 생성되는 것을 확인했고, 어제 손으로 만든 레코드는 폐기해 Convert 산출물로 단일화했다. PRM 제휴사 더미 데이터 105건을 넣었는데, 여기서 어제 우려했던 **Contact Default Record Type 문제가 실제 데이터로 터졌다.**

---

## 오늘의 목표

어제 만든 d'Alba Account를 열면 **Fan(팬) 화면이 뜬다.** Partner 레코드타입에 Layout·Compact Layout·Lightning Record Page·프로파일 할당이 전부 비어 있어 기본값을 상속받고 있었기 때문이다. 데모에서 "제휴사 관리 화면"이라며 열었는데 팬 프로필 항목이 나오면 그 장면 하나로 신뢰를 잃는다.

여기에 더해 ① Lead Convert가 실제로 어떻게 동작하는지 검증하고 ② B2B 파이프라인이 파이프라인처럼 보이도록 제휴사 더미 데이터를 채우는 것까지가 오늘 범위였다.

---

## 한 것

### 1. Lead Convert 실검증 — 한 번에 세 개가 생긴다

문서로만 알고 있던 걸 실제로 돌려봤다.

| 단계 | 레코드 | ID |
|---|---|---|
| 원본 | Lead `김하나` (Company = d'Alba(달바)) | `00Qbm00000nOmP3EAK` |
| → | Account `d'Alba(달바)` RecordType=Partner | `001bm00002heaKjAAI` |
| → | Contact `김하나` RecordType=**Partner** | `003bm00001jQU4rAAG` |
| → | Opportunity `d'Alba × Cloud Alpacas Sponsorship` | `006bm00000VSyIjAAL` |

Opportunity는 **₩300,000,000 / Stage = Qualification**으로 생성됐다. Convert 한 번에 B2B 파이프라인의 세 축이 동시에 만들어지고 서로 연결까지 된다 — 이게 Sales Cloud의 기본 동작이라는 걸 화면으로 확인했다.

Contact가 **Partner 레코드타입으로 생성된 것**도 확인했다. 어제 프로파일에 Partner RT를 할당해두지 않았다면 여기서 김하나가 Player로 만들어졌을 것이다.

### 2. 어제의 수동 생성분을 폐기하고 Convert 산출물로 단일화

어제는 *"지금 만들되 Convert 때 Choose Existing Account를 쓴다"*로 정했었다. 오늘 실제로는 **반대 방향으로 정리했다** — 어제 손으로 만든 Account `001bm00002hHfcrAAC`와 Contact `003bm00001jBk9xAAC`를 지우고, Convert가 새로 만들게 뒀다.

**왜 바꿨나** · Choose Existing Account 방식은 사람이 매번 올바르게 눌러줘야 성립한다. 어제 스스로 *"혜준님에게 전달되지 않으면 그 순간 무너진다"*고 적어놓고도 그 리스크를 안고 갈 이유가 없었다. **Account를 지우는 비용(레코드 1건)이 잘못 눌릴 리스크보다 훨씬 쌌다.** 결과적으로 `P2_DATA_CONTRACT` §3.5의 "Account는 Convert의 결과여야 한다"를 우회가 아니라 원문 그대로 만족하게 됐다.

> 🔴 **다만 승계되지 않은 것이 있다.** Convert로 생긴 Account는 **Industry·Type이 비어 있다** — 어제 채운 Industry = Cosmetics / Beauty, Type = Prospect가 넘어오지 않았다. Lead에 대응 필드가 없으면 Convert는 그냥 빈칸으로 만든다. **재입력이 필요하다.**

### 3. PRM 제휴사 더미 데이터 — Partner Account 105건

파이프라인이 "후보가 여럿 있는 것처럼" 보이려면 제휴사가 한 곳뿐이어선 안 된다. 국내 대기업 계열(삼성전자·LG전자·SK텔레콤·현대자동차·기아 등)로 **Partner Account를 105건 추가**했다 — Org 전체 Partner Account는 107건이 됐다.

같은 시간대에 Opportunity도 6건이 만들어져 Stage가 골고루 퍼졌다.

| Opportunity | Stage | 금액 |
|---|---|---|
| d'Alba × Cloud Alpacas Sponsorship | Qualification | ₩300,000,000 |
| Company Bloom | Proposal/Quote | ₩200,000,000 |
| Company Halo | Negotiation | ₩150,000,000 |
| Company Rhino | Discovery | ₩120,000,000 |
| Company Ever | **Closed Won** | ₩100,000,000 |
| Company Nova | Qualification | ₩80,000,000 |

Closed Won이 하나 있어야 *"작은 성공 → 큰 계약"* 서사가 성립한다는 8/14 설계가 데이터로 들어왔다.

### 4. Partner Account 화면 계층

Fan/Player 화면을 건드리지 않는다는 전제 위에서 전부 **신규 생성 후 Partner 레코드타입에만 할당**했다.

| 만든 것 | ID | 구성 |
|---|---|---|
| Page Layout `Partner Account Layout` | `00hbm00000XJoFp` | Account Name / Parent Account / Industry / Type / Partner Type / Website / Description / Phone / Account Owner / Billing Address / Account Record Type |
| Compact Layout `Partner Account Compact Layout` | `0AHbm000005BTmz` | Account Name / Industry / Partner Type / Website / Type / Phone / Account Owner |
| Lightning Record Page `Account - Partner Account` | `0M0bm00000DNF1ZCAX` | 기존 SDO 페이지 재사용 — **할당 8건** |
| Page Layout `Partner Contact Layout` | `00hbm00000XKI4E` | Name / Account Name / Title / Department / Email / Phone / Contact Owner / Contact Record Type / Description / Lead Source |
| List View `Partner Contacts` | — | 생성만 완료, 필터·컬럼 미정리 |

Page Layout은 **64개 프로파일 전체에 대해 Partner 레코드타입에만** 할당했다. Master / Account / Business Account 레이아웃, `Player - Contact` 컬럼은 모두 미변경.

Lightning Record Page 할당 8건의 내역 — Cloud Alpacas FRM·PRM **앱 2종** × Partner **레코드타입** × Standard User·System Administrator **프로파일 2종** × Desktop·Phone **폼팩터 2종**. 화면 하나를 바꾸는 데 할당이 8건 필요하다는 걸 이번에 처음 체감했다.

### 5. 레코드타입 정책 — 늘리지 않고 Partner Type으로 가른다

제휴사 종류(스폰서/리셀러 등)를 **레코드타입으로 나눌 것인가, 필드 값으로 나눌 것인가**를 정해야 했다.

**결정: Account 레코드타입은 `Partner` 하나만 유지하고, 구분은 Partner Type(`SDO_Partner_Type__c`) 값으로 한다.** 여기에 **`Sponsor` 값을 추가**했다.

**왜** · 레코드타입을 하나 늘리면 Page Layout·Compact Layout·Lightning Page 할당·프로파일 할당이 통째로 한 벌 더 붙는다. 오늘 8건의 할당을 직접 해보고 나서 이 비용이 실감났다. **화면이 똑같다면 레코드타입을 나눌 이유가 없다** — 필드 값 하나면 리포트·리스트뷰 필터도 다 된다.

### 6. Partner Account에서 Contact를 만들 때 Player가 보이지 않게

어제 남겨둔 과제였다. Contact 오브젝트의 Quick Action은 **레코드 페이지에만 배치되고 리스트뷰의 New 버튼은 대체하지 못한다.**

→ **Account 쪽에 액션을 두고, Partner Account Layout의 *Salesforce Mobile and Lightning Experience Actions* 영역에 배치**했다. 이렇게 하면 Account 화면에서 담당자를 추가하는 흐름이 되어 **레코드타입이 Partner로 고정되고 Account도 자동으로 채워진다.**

> 함정 · 그 Actions 영역은 처음엔 드래그가 안 된다. **"override the predefined actions" 링크를 먼저 눌러야** 편집이 열린다.

### 7. SDO 데모 레코드는 지우지 않고 격리

Org에는 SDO(Salesforce 데모 패키지) Lead·Opportunity가 각각 50건 넘게 있다. 지우는 게 깔끔해 보이지만 **패키지 의존성 때문에 삭제가 위험**하다 → **List View 필터(`[SCN-B2B-001]` 또는 RecordType)로 격리.** 되돌릴 수 없는 조치보다 되돌릴 수 있는 조치를 골랐다.

## 막힌 것

> 이 섹션이 포트폴리오에서 제일 값어치 있다. 문제 → 원인 → 해결 순서로.

### 레이아웃에 분명히 넣은 Account Name이 화면에 아예 안 뜬다

Contact 레이아웃에 Account Name을 배치해 저장했는데 Details 탭에도 Edit 창에도 **필드가 렌더링되지 않았다.** 에러 메시지도 없다. 편집기로 돌아가면 필드는 멀쩡히 그 자리에 있다.

**원인** · 두 겹이었다.

1. 편집기에서 Title을 Account Name **행 위에 드롭**해 덮어써 버렸다. 눈으로 보고 바로 고쳤다.
2. 고친 뒤에도 안 떴다. 진짜 원인은 **`Contact.AccountId`의 필드 수준 보안(FLS)이 Read-Only**였던 것 — 라벨만 나오고 입력칸이 없었다.

**해결** · Object Manager → Contact → Fields → Account Name → Set Field-Level Security → Read-Only 해제.

**배운 것** · **"화면에 필드가 안 보인다"는 증상은 레이아웃 문제가 아닐 수 있다.** Salesforce에서 필드가 보이려면 최소 세 겹이 통과해야 한다 — ① 레이아웃 배치 ② FLS ③ 레코드타입에 그 레이아웃이 할당. 어제의 레코드타입 오류도 같은 종류였다. **"존재한다"와 "이 사용자에게 보인다"는 항상 다른 문제다.**

### PRM 담당자 107건이 전부 Player(선수)로 들어갔다

어제 *"Contact Default Record Type을 Player로 두면 제휴사 담당자가 선수로 생성된다"*고 팀에 올렸는데, **결정이 나기 전에 그 일이 실제로 일어났다.**

오늘 생성된 Contact를 레코드타입별로 세어보니 이렇다.

```
RecordType = Player   107건   ← PRM 제휴사 담당자
RecordType = Partner    1건   ← 김하나 (Lead Convert 산출물)
```

게다가 이름이 `삼성전자`, `LG전자`, `SK텔레콤`처럼 **회사명 그대로**다 — CSV의 회사명 컬럼이 Contact의 성(LastName)으로 들어갔다.

**원인** · 두 가지가 겹쳤다. ① Contact의 Default Record Type이 Player라, 레코드타입을 명시하지 않고 넣으면 전부 Player가 된다. ② 더미 데이터 매핑에서 담당자 이름 대신 회사명이 들어갔다.

**해결(진행 중)** · 아직 정리 중이다. 레코드타입은 일괄 Update로 Partner로 바꿀 수 있지만, **이름은 정리가 아니라 다시 만드는 쪽이 맞다** — 제휴사 담당자는 사람 이름이어야 데모에서 "박부장에게 연락" 같은 장면이 성립한다.

**배운 것** · **위험을 문서에 적어두는 것과 막는 것은 다르다.** 어제 이 리스크를 정확히 짚어 팀에 공유까지 했지만, 결정을 기다리는 사이에 대량 적재가 먼저 지나갔다. 대량 적재처럼 **되돌리는 비용이 큰 작업 앞에는, 미결 항목이 있으면 적재를 멈추는 게 맞다.** 지금 107건을 고치는 시간이 그때 결정을 기다렸을 시간보다 훨씬 길다.

### Partner Type에 Sponsor를 추가했는데 실제로는 선택할 수 없다

Partner Type(`SDO_Partner_Type__c`)에 `Sponsor` 값을 추가했다. 그런데 Org를 조회해보니 이렇다.

```
마스터 값 세트     Partner / Reseller / Distributor / Alliance Partner /
                  Service Provider / System Integrator /
                  Service & Support Specialist / Sponsor   ← 8개
Partner 레코드타입  위 7개 (Sponsor 없음)
```

이 상태로 Partner 레코드에 Sponsor를 넣으면 `INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`가 난다.

**원인** · 픽리스트 값은 **① 마스터 값 세트에 추가**하는 것과 **② 각 레코드타입의 값 세트에 포함**시키는 것이 별개 단계다. ①만 하고 ②를 안 했다.

**해결(미완)** · Object Manager → Account → Record Types → **Partner** → Picklists 섹션의 Partner Type → Edit → Available Values에서 Sponsor를 Selected로 이동.

**배운 것** · 오늘만 세 번째다 — 레코드타입 권한, FLS, 그리고 이번 픽리스트. **Salesforce에서 무언가를 "추가했다"는 것은 거의 항상 "만들었다 + 노출시켰다" 두 단계다.** 만들고 나서 실제 화면에서 한 번 눌러보지 않으면 절반만 한 것이다.

## 팀에 공유할 것

혼자 정할 수 없는 것, 다른 사람 작업에 영향 가는 것.

1. **@조혜준 — Lead Convert는 검증 완료다.** 어제 안내한 "Choose Existing Account"는 **더 이상 필요 없다.** 어제 손으로 만든 Account·Contact를 지웠으므로 평소대로 Convert하면 된다. 유효한 d'Alba Account는 `001bm00002heaKjAAI` 하나뿐이다.
