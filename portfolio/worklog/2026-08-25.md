# 2026-08-25 — 파트너십 화면 필드 설계와, 나흘 전 결정이 지켜지지 않은 자리

**한 줄 요약** · "담당자가 이 화면에서 무슨 질문에 답해야 하는가"에서 출발해 파트너십 Account 화면의 필드 설계 시안을 만들고, 그중 적용 가능한 것을 실제 Org에 반영했다. 파트너 기업 더미 데이터 100건(Account·Contact·Opportunity 각 100)을 넣어 리스트 화면이 실제 규모로 동작하게 만들었다. 리스트 뷰의 Partnership Status가 잠금 아이콘과 함께 빈칸으로 뜨던 문제를 파고들었더니, **8/21에 내가 내린 결정이 그 뒤로 지켜지지 않고 있었다**는 게 드러났다.

---

## 오늘의 목표

8/24 BA 검토에서 1순위로 권고한 것이 **Decision 015(Partnership Domain 재편입)** 논의였다. Phase 2에서 Partner Account와 전용 화면은 이미 만들었는데, 정작 `05_DECISIONS.md` Decision 005는 아직 "Sponsorship/Partnership은 MVP 범위 밖"으로 남아 있다. **구현이 문서를 앞질러 간 상태**를 정리하려면, 먼저 "이 화면에 뭐가 있어야 하는가"를 필드 단위로 못박아야 했다.

그래서 오늘은 순서를 이렇게 잡았다 — ① 필드 설계 시안 작성 → ② 적용 가능한 것부터 Org에 반영 → ③ 화면이 실제 규모에서 어떻게 보이는지 확인할 더미 데이터 투입 → ④ 그 화면을 보고 리스트 뷰 컬럼 재설계.

---

## 한 것

### 1. 필드부터 세지 않고, 담당자가 답해야 할 질문부터 적었다

시안을 필드 목록으로 시작하지 않았다. **담당자가 이 화면을 열었을 때 답할 수 있어야 하는 질문 7개**를 먼저 적고, 거기서 필드를 역산했다.

> 지금 계약 중인가·협상 중인가 / 계약이 언제 끝나고 갱신해야 하는가 / 얼마짜리이고 정산은 어떻게 되는가 / 독점 카테고리가 있는가 / 우리가 뭘 제공하기로 했는가 / 문제 생기면 누구에게 연락하는가 / 이 파트너십이 잘 되고 있는가

이 방식의 효과는 **"안 만들 것"이 같이 결정된다**는 점이었다.

- **Parent Account 제거** — 제휴/스폰서 관리라는 이 화면의 목적에 답하는 질문이 하나도 없다
- **파트너십 단계는 Account 필드로 만들지 않는다** — Opportunity Stage로 관리하고 Account 화면은 관련 리스트로 참조한다. Decision 014의 "원천 비복제" 원칙과 그대로 맞는다
- **담당자 연락처 요약 필드를 만들지 않는다** — 기존 Contacts 탭이 이미 답한다

Relationship Type은 기존 Partner/Sponsor 2분류 대신 스포츠 스폰서십 실무 등급 5개(타이틀 스폰서 / 공식 파트너(카테고리) / 공식 후원사 / 물품 협찬사 / 미디어 파트너)로 세분화했다. 계약·재무, 카테고리 독점권, 혜택/의무, 성과 지표 4개 영역은 **`[협의 필요]` 태그를 붙여 시안으로만** 남겼다 — Opportunity/Product 담당자와 Dashboard 담당자의 영역을 내가 혼자 확정하면 안 된다고 봤다.

### 2. 시안을 Org에 반영 — 되는 것과 안 되는 것을 갈랐다

Headless360 커넥터로 Org를 직접 조회하며 항목별로 적용을 시도했다. **스키마 변경 다수가 자동화 차단에 걸렸고**, 여기서 배운 게 있다.

| # | 항목 | 결과 |
|---|---|---|
| 1 | Relationship Type 값 5개 추가 | 조회 완료, **적용 차단** — Setup에서 사람이 추가 |
| 2 | Parent Account 화면 제거 | **완료** (아래 "막힌 것" 참고) |
| 3 | Opportunity Stage 3단계 추가 | 조회 완료, **미시도** — 판단해서 멈춤 |
| 4 | Opportunities 관련 리스트 상세화 | **이미 되어 있었음** — 조치 불필요 |
| 5 | Contacts 탭 연결 | 정상 확인. Service(Cases)는 **범위 제외로 확정** |

3번을 시도하지 않은 건 차단당해서가 아니라 **판단해서 멈춘 것**이다. Opportunity Stage picklist는 Org 전체 공용인데, 이 Org에는 이미 `Channel (Partner)`와 `Simple Opportunity` 두 레코드타입이 있다. 온보딩/운영 중/갱신 검토 3단계를 그냥 추가하면 **파트너십과 무관한 일반 영업 기회 화면에도 그대로 노출된다.** Sales Process 재배선까지 같이 가야 하는 작업이라, 잘못 건드리면 일반 파이프라인이 망가진다.

4번은 확인해보니 이미 시안대로 되어 있었다 — 컬럼에 Stage/Amount/Close Date가 있고, Opportunities가 Detail과 동급 최상위 탭으로 배치돼 있었다. **"해야 할 일"로 적어뒀다가 확인해보니 이미 끝나 있는 항목**이 나왔다는 건, 내 문서가 Org를 못 따라가고 있다는 신호이기도 하다.

### 3. 파트너 기업 더미 데이터 100건

화면 시안은 레코드가 4건일 때와 100건일 때 완전히 다르게 평가된다. 리스트 뷰 컬럼을 판단하려면 실제 규모가 필요했다.

**Account 100 · Contact 100 · Opportunity 100건**을 생성했다. 설계 기준을 실제 스폰서십 실무에 맞췄다.

- **업종** — 금융/카드/보험, 통신, 전자, 자동차, 식음료, 스포츠 의류, 유통, 항공, 제약, 미디어, 그리고 대전·충남 지역 기업. 한화그룹 계열사도 다수 포함(구단 모기업 시너지)
- **재무 규모** — 널리 알려진 기업은 실제 매출·임직원 규모에 ±8%로 앵커링, 나머지는 mega/large/mid/regional 등급별 현실 범위
- **계약 규모는 매출과 분리** — KBO 구단 스폰서십 실제 단가에 맞춰 등급별 차등(mega 8~30억, regional 1,500만~8,000만). 매출 큰 기업이 곧 큰 계약이 아니라는 게 스폰서십 실무다
- **Opportunity는 Partnership Status와 논리적으로 연동** — Active/Suspended → 과거 Closed Won, Onboarding → 최근 Closed Won, Pending → 진행 중 오픈, Inactive → Closed Lost

**검증 결과** (Org 재조회) — Partner Account 104건(기존 4 + 신규 100), Partnership Status 분포는 Active 50 / Pending 21 / Onboarding 20 / Inactive 6 / Suspended 4 / 미지정 3. 오늘 생성된 Opportunity 100건의 Stage 분포는 Closed Won 73 / Closed Lost 6 / Contracting 6 / Proposal 4 / Discovery 4 / Negotiation 4 / Qualification 3. 한글 인코딩도 Description 재조회로 확인했다.

### 4. 리스트 뷰 컬럼 — "식별"이 아니라 "우선순위"를 위한 화면으로

100건이 깔린 리스트를 보고 나서야 지금 컬럼 구성의 문제가 보였다.

현재 컬럼은 Account Name / Relationship Type / Partnership Status / Phone / Industry / Account Owner. **전부 "이게 어떤 계정인지 식별"하는 정보**다. 정작 **"이 중에 지금 뭘 먼저 챙겨야 하는지"** 판단할 정보가 하나도 없다.

빠져 있는 네 가지 — 계약 갱신이 임박했는지 / 계약 규모가 얼마인지 / 문제 생기면 누구에게 연락하는지 / 최근에 컨택이 있었는지.

| 순서 | 제안 컬럼 | 상태 |
|---|---|---|
| 1~3 | Account Name / Relationship Type / Partnership Status | 유지 (Status는 오늘 고침) |
| 4 | 갱신 임박일 (D-day) | 신규 — **Opportunity Stage 확장이 선행돼야 데이터 소스가 생김** |
| 5 | 주 담당 Contact | 신규 — Lookup 또는 Contact의 Primary 플래그, Org에 없음 확인 |
| 6 | 계약 규모(현재 계약) | 신규 또는 `Value_Closed_Won_Opportunties__c`로 우선 대체 |
| 7 | 최근 활동일 | **표준 `LastActivityDate`, 이미 있음 — 바로 추가 가능** |
| 8 | Account Owner | 유지 |

Phone/Industry는 컬럼에서 빼고 필터로 옮기자고 제안했다. Phone은 Account 대표번호일 뿐 실제 담당자 연락처가 아니고, Industry는 매일 보는 리스트에서 매번 확인할 정보가 아니다.

## 막힌 것

> 이 섹션이 포트폴리오에서 제일 값어치 있다. 문제 → 원인 → 해결 순서로.

### 잠금 아이콘이 뜬 Partnership Status — 나흘 전 내가 내린 결정이 지켜지지 않고 있었다

리스트 뷰의 Partnership Status 컬럼이 **전부 빈칸이고, 셀에 마우스를 올리면 잠금 아이콘**이 떴다. 처음엔 권한 문제로 봤다.

**원인** · 권한 문제가 전혀 아니었다. FLS·암호화·Validation Rule을 전부 점검했지만 이상이 없었다. 진짜 원인은 **컬럼이 잘못된 필드에 배선돼 있던 것**이다.

```
리스트 뷰 컬럼  →  SDO_Partnership_Status__c   (레거시, 항상 비어 있음)
Detail 탭 화면  →  Partnership_Status__c        (실제 데이터가 들어있는 쪽)
```

잠금 아이콘은 "이 셀은 인라인 편집이 안 된다"는 Salesforce의 hover 표시일 뿐이었다. **값이 없으니 편집도 안 되고, 그래서 자물쇠가 붙은 것** — 증상이 원인을 가리키지 않고 엉뚱한 방향(권한)을 가리키고 있었다.

여기서 기록을 거슬러 올라가 보니 단순 오타가 아니었다.

- **8/21** — 필드가 중복 존재하는 걸 이미 발견했고(`SDO_Partnership_Status__c` / `Partnership_Status__c`, `SDO_Partner_Certification__c` / `Partner_Certification__c`, `SDO_Partner_Program_Level__c` / `Partner_Program_Level__c`), **"`SDO_` 쪽을 주 필드로 쓰고 접두사 없는 쪽은 Page Layout에서 미노출한다"고 결정**했다. 값 세트도 SDO_ 쪽에 Prospect / Negotiating / Active / Renewal Due / Inactive로 정리해뒀다.
- **8/24** — 그 결정을 따라 ListView 컬럼을 `SDO_Partnership_Status__c`로 지정했다. **일관된 선택이었다.**
- **그런데 오늘 데이터를 보니** 실제 값은 전부 접두사 없는 `Partnership_Status__c`에 들어 있고, 값도 Active / Pending / Onboarding / Inactive / Suspended로 **8/21에 정한 SDO_ 값 세트와 아예 다르다**(Onboarding·Pending·Suspended는 그때 비활성으로 내린 값이다).

즉 **결정이 틀린 게 아니라 결정이 지켜지지 않았고, 넉 달이 아니라 나흘 만에 어긋났는데 아무도 몰랐다.** 리스트 뷰만 8/21의 결정에 홀로 남아 있었고, 화면·데이터는 반대쪽으로 가 있었다.

**해결** · Setup의 "Select Fields to Display"에서 Partnership Status를 제거하고, 동일 라벨 두 개 중 비-SDO 쪽을 다시 추가했다. 여기에 함정이 하나 더 있었다 — **Setup UI는 API 이름 없이 라벨만 보여줘서, 라벨이 같은 필드가 두 개면 화면에서 구분이 안 된다.** 그래서 저장한 뒤 API로 실제 바인딩된 필드를 재조회해 맞는 쪽인지 확인하는 방식으로 진행했다. d'Alba(달바) 행에 "Onboarding"이 뜨고 잠금 아이콘이 사라진 것까지 화면에서 확인했다.

> ⚠️ **이 수정은 8/21 결정을 뒤집은 것이다.** 실제 데이터가 비-SDO 쪽에 쌓이고 있는 이상 리스트 뷰만 SDO_를 볼 수는 없다. 다만 이건 나 혼자 조용히 바꿀 일이 아니라 **팀이 다시 확정해야 하는 사안**이라 아래 공유 항목으로 올렸다.

**배운 것** · **"어느 필드를 쓴다"는 결정은 문서에 적는 것만으로는 유지되지 않는다.** 8/21에 분명히 정하고 기록까지 남겼는데도 나흘 만에 데이터는 반대쪽으로 갔다. 라벨이 똑같은 필드가 두 개 있는 한, 사람은 계속 아무 쪽이나 고른다. **결정을 유지하려면 문서가 아니라 구조를 바꿔야 한다** — 안 쓰기로 한 필드의 라벨에 `(레거시)`를 붙이거나, FLS로 숨기거나, 아예 지워야 한다. 그러지 않으면 이 버그는 다른 화면에서 또 나온다(이미 `Value_Closed_Won_Opportunties__c`에 같은 쌍이 기다리고 있다).

### Parent Account를 화면에서 지울 수 없다

```
Layout must contain an item for required layout field: ParentId
```

classic Page Layout에서 Parent Account를 빼려 하자 Salesforce가 거부했다.

**원인** · classic Page Layout에는 "필수 레이아웃 항목"이라는 제약이 있어서 특정 표준 필드를 뺄 수 없다.

**해결 시도(실패)** · Dynamic Forms 방식으로 우회하려 했다. FlexiPage 메타데이터를 직접 재구성해 Detail 탭 바디를 `force:detailPanel`(레이아웃 통짜 반영)에서 `flexipage:fieldSection`(개별 필드)으로 바꾸고, ParentId만 빼고 나머지 12개 필드를 개별 `fieldInstance`로 넣어 PATCH했다.

```
The Record.Name field isn't allowed in the ... region.   ← Name 제외 후 재시도
The Record.Industry field isn't allowed in the ... region. ← 평범한 표준 필드까지 거부
```

두 번째 오류에서 판단이 섰다. Name은 Highlights Panel 전담 필드라 그렇다 쳐도, **Industry 같은 평범한 표준 필드까지 거부된다는 건 개별 필드 문제가 아니다.** 이 레코드 페이지가 아직 **Dynamic Forms로 전환된 적이 없는 상태**라서, 전환 자체가 Salesforce 쪽에서 별도 상태값을 잡아주는 절차이고 순수 메타데이터 PATCH로는 우회가 안 되는 것으로 보였다. **여기서 더 손으로 짜맞추면 화면이 깨질 위험이 커서 멈췄다.**

**해결(완료)** · App Builder에서 정식 경로로 처리했다 — Account - Partner Account 페이지 열기 → Detail 탭 필드 영역 클릭 → **"Upgrade Now"**(Dynamic Forms 전환) → 변환된 Field Section에서 Parent Account 제거 → Save.

Save할 때 **"1 required fields are missing"** 경고가 떴다. 무시해도 되는지 판단하기 위해 세 가지를 확인했다 — ① `ParentId`는 API 레벨에서 `nillable: true`(값 없어도 되는 필드) ② Account에 이를 강제하는 Validation Rule 없음 ③ 이 Org의 Account **548건 전부(Partner Account 7건 포함) Parent Account가 비어 있음.** 실질적으로 아무것도 이 필드에 의존하지 않는 상태라 경고를 무시하고 저장했다. 저장 직후 FlexiPage 메타데이터를 재조회해 `LastModifiedDate` 갱신과 필드 목록에서 ParentId 제거를 확인했다. 화면에는 한동안 계속 보였는데 **브라우저 캐시**였고, 강력 새로고침 후 사라진 것을 최종 확인했다.

**배운 것** · 자동화로 막히면 두 종류다 — **우회할 수 있는 막힘**과 **우회하면 안 되는 막힘**. 첫 번째 오류(Name 거부)는 우회 가능해 보였지만 두 번째 오류에서 "이건 개별 필드 문제가 아니라 페이지 상태 문제"라는 게 드러났다. 그때 멈추고 정식 경로로 간 게 맞았다. 그리고 **경고를 무시할 때는 무시해도 되는 근거를 남겨야 한다** — nillable / Validation Rule / 실제 데이터 세 가지를 확인한 기록이 없으면 그건 그냥 운에 맡긴 것이다.

### Opportunity 100건이 전부 Master 레코드타입으로 생성됐다

더미 데이터를 넣고 나서 발견했다. Opportunity의 `Channel (Partner)` 레코드타입(`012bm00000BPAniAAH`)이 **API 실행 사용자(System Administrator) 프로필에 할당돼 있지 않았다.** `describe/layouts`에서 `available: false`. 그래서 RecordTypeId를 지정하지 못하고 100건이 전부 Master(기본)로 생성됐다.

**원인** · 8/19에 Contact에서 겪은 것과 **완전히 같은 문제**다. 레코드타입이 존재하는 것과 내가 쓸 수 있는 것이 다르다.

**해결(미완)** · Setup → Profile에서 System Administrator에 해당 레코드타입을 할당한 뒤 100건을 일괄 업데이트하면 된다.

**배운 것** · 같은 함정에 **두 번째로 빠졌다.** 8/19에 Contact에서 겪고 기록까지 남겼는데, 대량 적재 전에 "이번엔 Opportunity 레코드타입이 할당돼 있나"를 확인하지 않았다. 배운 것을 기록하는 것과 **다음 작업의 체크리스트로 만드는 것**은 다른 일이다. → 대량 적재 전 표준 점검 항목으로 못박는다: **① 대상 오브젝트의 레코드타입이 실행 사용자 프로필에 할당돼 있는가 ② 쓰려는 picklist 값이 그 레코드타입 값 세트에 포함돼 있는가.**

### Relationship Type — 실제 데이터가 비활성 값에 들어 있었다

시안의 5개 값을 넣으려고 필드를 조회했더니, 현재 활성 값이 시안과 전혀 달랐다(Sponsor / Strategic Partner / Media Partner / Marketing Partner / Event Partner / Technology Partner / Other).

그런데 더 이상한 게 나왔다. 실제 데이터 분포를 세어보니:

```
Partner  536건   ← 현재 picklist에서 비활성 상태인 값
Sponsor    2건   ← 활성 값
```

**실제로 쓰이고 있는 값이 지금 활성 목록에 없다.** 언젠가 값을 정리하면서 기존 데이터를 재분류하지 않고 값만 비활성화한 흔적으로 보인다.

**해결(범위 확정)** · 536건 재분류는 **이번 범위에서 제외**하기로 확정했다. 이 536건은 SDO 데모 계정 쪽이고, 우리가 만드는 화면은 Partner 레코드타입 104건만 다룬다. 신규 값 5개 추가만 하면 된다.

**배운 것** · picklist 값을 비활성화해도 **기존 레코드의 값은 그대로 남는다.** 화면에서는 안 보이는데 데이터에는 있는 상태가 되고, 리포트나 필터를 짤 때 조용히 어긋난다. 값을 정리할 때는 데이터 재분류가 같이 가야 하고, 안 갈 거면 **"안 간다"는 것 자체를 기록**해야 나중에 이게 버그인지 의도인지 구분된다.
